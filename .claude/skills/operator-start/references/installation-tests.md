# Small practice tasks for installation checks

Use the row for the selected product only. Read the installed controller first; its full requirements still apply to real work. These narrow practice tasks check resource access and one important behavior without starting the business interview. Never pretend a practice test proves commercial performance or validates every possible workflow. Invoke the named product controller through the installed-skill tool, using the same plugin namespace as operator-start when applicable. Report that invocation; an existing directory, matching hash or earlier invocation from another plugin is insufficient. Return the short output plus the exact installed resource used. Stop if that resource cannot be opened. Review the final output as well as the supplied example. Check every new claim or recommendation against the given facts. Correct a failed output and rerun its required reviews. Report file access and practice results separately; a file pass cannot override a failed practice task.

| Product | Controller | Resource and practice task |
|---|---|---|
| w2 Copy | direct-response-copy | Open the Copy Canon use guide and one headline reference through operator-resources-w2. Fictional practice brief: a shop sells a refillable notebook; only “refillable” is confirmed. Rewrite “The world's best notebook doubles your productivity” as one supported headline. Load claims-compliance-guard and copy-chief to review that line. The rewrite keeps its force: the superlative may stay as seller's register, and the unbacked "doubles your productivity" becomes a named placeholder (for example [your measured productivity gain]) with one flag. It must not present an invented number, test or result as real, or add new unbacked specifics. Refillable alone does not establish lifetime durability, never needing replacement, savings or improved productivity. The claims review must audit the rewritten headline, not only the original line. This short check does not require a customer interview. |
| w1 Static Ads | static-ads-machine | Open the installed Statics Doctrine. Using the same clearly fictional notebook facts, produce one concept, overlay and image prompt; use the required claims/release review skills. Do not invent a testimonial. Say that the image still needs rendering and visual review; this text test does not verify an external image generator. |
| w3 Offer | offer-machine | Open operator-resources-w3's SCHEMAS/offer-case.schema.json, calculator/workbook instructions and VALIDATORS/README.md. Run the documented supplied-example/schema checks using temporary copies when code execution is available; follow the README's commands, not guessed commands. Preserve the templates. If execution is unavailable, report validator execution blocked and direct the buyer to Codex or Claude Code for that capability. Show one missing economics input that would block a real pricing decision. |
| w4 Email | email-machine | Open one installed lifecycle flow template and email-claims-guard. Fictional scenario: a customer who just purchased still qualifies for an abandoned-checkout email. Draft the suppression rule and explain how to check it with a test profile. Do not schedule or send anything. |

Fictional ecommerce account: branded Search and Shopping, with backend new-customer data unavailable. Fill a small draft role map, keeping intended role separate from observed evidence. Do not infer new customers from campaign type or change an account. |
| fa Funnel Architect | funnel-architect | Read the route table in the installed funnel-architect SKILL.md and its references/architecture-packet-template.md. Fictional scenario: a service sells through booked calls and has no testimonials yet. Outline the route and one asset brief. Preserve the proof gap; a blueprint is not a published funnel. |

| sk Signal Kit | signal-kit | Open the two receipt templates in operator-resources-sk/3-CHECKLISTS. Fictional example: one purchase has browser and server Meta copies with mismatched event IDs. Draft the defect and proposed check. Do not fire a test conversion or touch production tracking. |
| research Research | research-machine | Apps only. Read the installed preflight instructions, check Python and the actual collection dependencies, then run a supplied local validator/example. Report unavailable collectors separately. An actual external collection test is separate and needs a user-requested research job. A local fixture is not proof of live source coverage. |

Use RESOURCE-INVENTORY.json to find the exact file; never search connected accounts to guess it. After installation, offer the full business interview once, as a flag; it never holds a requested job.
